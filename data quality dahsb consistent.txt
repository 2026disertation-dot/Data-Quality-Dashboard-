
Designing a data Quality Dashboard for Detecting Inconsistencies in Multi-Project Portfolios
CHAPTER 1
INTRODUCTION
1.1 Background
Data quality is a foundational requirement for reliable decision-making in modern organisations. In today's data-driven world, the integrity, accuracy, and consistency of data determine whether analytical results can be trusted and whether operational decisions are sound. Data quality is defined by several dimensions, namely completeness, consistency, accuracy, integrity, reliability, and timeliness, which together determine whether information is suitable for its intended use (Batini and Scannapieco, 2016). When any of these dimensions is compromised, the consequences extend beyond the immediate data record: analysis becomes unreliable, decisions become misinformed, and organisational outcomes deteriorate (Wang and Strong, 1996; Hevner et al., 2004).
This general problem becomes particularly acute in project portfolio management, where decisions about expenditure, performance, and resource allocation depend on the quality of recorded cost data. In multi-project environments, inaccurate or incomplete budget and actual cost records can distort cost variance calculations, undermine estimates at completion, and reduce the reliability of portfolio-level forecasts. The four dimensions of data quality, namely completeness, consistency, accuracy, and integrity, therefore become operational requirements rather than abstract ideals, because they determine whether project cost information can support the decisions that portfolio managers must make.
Empirical studies have demonstrated that the consequences of poor data quality in project environments are financially material. Flyvbjerg et al. (2004), analysing 258 transport infrastructure projects, found systematic cost underestimation in approximately 90% of cases, establishing that the problem is not random but structural. Love et al. (2010) attributed a significant proportion of civil infrastructure rework to information quality failures rather than to construction or design errors. These findings establish that data quality in project cost records is not merely an administrative concern but a direct contributor to cost overruns and project failure.
Maintaining these dimensions becomes more challenging when records originate from different projects and enter a system at different times. Traditional spreadsheet-based checks can identify certain errors, but their effectiveness depends on the checks implemented and the consistency with which users apply them. Furthermore, validating historical files does not necessarily prevent malformed records from entering a system through subsequent submissions. A data quality solution should therefore support systematic assessment of existing records while applying consistent validation rules to incoming data.
This study develops and evaluates an interactive data quality dashboard that combines historical data analysis with a live Flask application programming interface (API). Guided by Design Science Research, the project develops a software artefact and evaluates its performance against spreadsheet-based checks (Hevner et al., 2004; Myers et al., 2011). The study focuses on identifying, visualising, and prioritising inconsistencies in budget and actual cost records across multi-project portfolios.
1.2 Research Problem
The central research problem is how to detect and communicate data quality inconsistencies consistently across historical records and incoming cost submissions. Missing values, invalid data types, inconsistent field relationships, and implausible numerical values can compromise subsequent analysis. When validation rules differ between processing methods, the same record may receive different outcomes depending on how it enters the system.
A dashboard that only analyses historical files cannot, by itself, provide synchronous validation of incoming records. Conversely, an API that validates individual submissions without sharing the rules used for historical analysis may produce inconsistent results. The technical challenge is therefore to integrate validation, error reporting, and visualisation through a common data contract.
The gap this study addresses is the absence of a framework in project controls that combines multi-mode validation across batch, incremental, and live API channels with a synchronous endpoint and a unified data contract. The literature review in Chapter 2 establishes this absence in detail; the consequence is that undetected inconsistencies can propagate silently into cost variance calculations and portfolio forecasts before they are discovered, at which point the reliability of the indicators that practitioners depend on has already been compromised.
The study investigates whether a shared validation contract can support consistent checking across batch, incremental, and live API processing while enabling users to interpret and prioritise detected inconsistencies. It also compares the proposed dashboard with spreadsheet-based checks under defined testing conditions. These comparisons provide a basis for evaluating the artefact rather than assuming that automation necessarily produces better outcomes.
1.3 Research Aim and Objectives
Research Aim
To design, implement, and empirically evaluate an interactive data quality web dashboard with live API validation that detects, visualises, and prioritises inconsistencies in budget and actual cost records across multi-project portfolios.
The six objectives address the theoretical, analytical, technical, visualisation, evaluation, and integration activities required to achieve this aim.
Objective 1: Theoretical and Architectural Foundation. To establish a coherent theoretical and architectural framework by synthesising data quality dimensions, project cost-control principles, and dashboard design knowledge, and by defining a conceptual data contract that governs multi-mode operation.
Objective 2: Systematic Profiling and Metric Definition. To systematically profile the Project Portfolio Dataset and define quantitative metrics and detection rules for completeness, consistency, accuracy, and integrity across batch, incremental, and live API modes, and to quantify the impact of detected inconsistencies on cost variance, estimate accuracy, and portfolio-level forecasting reliability.
Objective 3: Pipeline Design and Live API Implementation. To design and implement a modular Python pipeline and validation engine that enforces the formal data contract in batch, incremental, and live API modes, including a live Flask API endpoint that validates incoming records synchronously, returns structured error responses, and writes all outcomes to a flagged-records log (with persistent storage identified as a future enhancement).
Objective 4: Interactive Visualisation and Prioritisation. To design and implement an interactive dashboard that visualises and prioritises data quality inconsistencies, communicates validation failures clearly for both batch and incremental data, and supports practitioner decision-making.
Objective 5: Empirical Evaluation. To evaluate the effectiveness, efficiency, and technical reliability of the dashboard against traditional spreadsheet-based quality checks under batch, incremental, and live API submission conditions through structured system testing.
Objective 6: Integration and Multi-Mode Consistency Assurance. To integrate the diagnostic, backend, frontend, and evaluation components into a coherent artefact and to ensure multi-mode consistency across the entire system, so that the same data contract and validation logic apply identically to batch, incremental, and live API data.

1.4 Research Questions
The study addresses three research questions:
RQ1. What data quality inconsistencies exist in budget and actual cost records, and how can they be systematically profiled across completeness, consistency, accuracy, and integrity dimensions?
RQ2. How can an interactive Python dashboard with a live Flask API endpoint be designed to visualise, validate, and support improvement of data quality across batch, incremental, and live API modes?
RQ3. How effective is the dashboard compared with traditional spreadsheet-based quality checks under batch, incremental, and live API submission conditions?
Each question is answered through a distinct form of evidence. RQ1 is answered through exploratory data profiling and descriptive statistics on the Project Portfolio Dataset, reported in Chapter 6. RQ2 is answered through the design and implementation of the artefact, with evidence drawn from the system architecture and from functional, integration, and boundary testing reported in Chapters 4 and 5. RQ3 is answered through comparative testing against spreadsheet-based checks, with evidence drawn from detection completeness, processing time, and technical reliability measures reported in Chapters 5 and 6.
The questions connect diagnosis, system development, and evaluation in a logical sequence. RQ1 establishes what inconsistencies exist; RQ2 addresses how a system can be designed to detect them consistently; RQ3 evaluates whether that system performs better than existing practice. Objectives 1 and 6 provide the theoretical and integration foundations supporting all three questions. 1.5 Scope and Delimitations
The study focuses on budget data, including the Performance Measurement Baseline (PMB), and actual cost records within multi-project portfolios. Schedule and resource data are excluded because they require different validation rules and fall outside the defined research aim.
The project uses the publicly available Project Portfolio Dataset, which contains 12,139 time-phased actual cost records from eight principal project workbooks over just under 109 consecutive weeks (gacevedob, 2022). The dataset documentation describes six of these workbooks as primary projects; the remaining two are treated as supplementary cases. Both are used because cross-project consistency rules are tested more strongly when there are more projects to compare, and the choice is stated explicitly in Chapter 3 (Section 3.3.1). Its use supports reproducibility, although findings remain bounded by the dataset's characteristics and the validation rules implemented. Reproducibility is further supported by the configuration-driven pipeline described in Chapter 4, which ensures that validation rules and processing behaviour are identical across development, testing, and demonstration environments.
The system uses Python, Streamlit for the interactive dashboard, Flask for the live API, Pandas and NumPy for data manipulation, Plotly for visualisation, Pandera for declarative schema specification, Great Expectations for supplementary validation, Pytest for testing, Git for version control, and YAML/JSON for runtime configuration. In this dissertation, product names are capitalised in prose (Pandas, Pandera, Pytest), while code identifiers retain their lowercase form (pandas.read_excel, pandas.to_datetime). The rationale for these technology choices is presented in Chapter 3.
The evaluation covers batch, incremental, and live API validation, including comparison with spreadsheet-based checks. It does not include longitudinal organisational deployment or real-world user trials. Consequently, the study evaluates technical performance under defined conditions rather than establishing long-term operational effectiveness or general usability across organisations.
1.6 Significance of the Study
The study is of value to project controls practitioners who require real-time validation of cost submissions, and to researchers developing data quality frameworks for project portfolios. It makes four intended contributions.
First, it develops a data quality dashboard that combines historical analysis with live API validation. This provides a practical means of identifying inconsistencies in existing records and validating incoming submissions.
Second, the shared data contract provides a basis for examining whether validation rules produce consistent outcomes across processing modes. This is assessed through structured testing rather than assumed from the architecture alone.
Third, comparison with spreadsheet-based checks enables the study to examine detection effectiveness, processing efficiency, and technical reliability under defined conditions. Reporting these measures can clarify the strengths and limitations of automated validation relative to the selected baseline.
Finally, interactive visualisations and structured error responses are intended to make validation outcomes easier to interpret and prioritise (Few, 2013). Together, these contributions connect data quality assessment with practical monitoring of project cost information. Their significance, however, depends on the empirical results and remains limited by the dataset, test design, and absence of field deployment.

CHAPTER 2
LITERATURE REVIEW AND DESIGN REQUIREMENTS
2.1 Introduction
This chapter argues that data quality management in project cost contexts has been treated predominantly as a batch-oriented, one-time activity, and that the absence of a unified validation framework operating consistently across batch, incremental, and live modes constitutes a genuine and consequential research gap. The argument proceeds through four bodies of literature: data quality dimensions, data quality frameworks, data consistency in project cost management, and data quality tools and dashboards. The gap emerges at their intersection: no existing framework in project controls combines multi-mode validation with a live synchronous endpoint and a unified data contract (Batini and Scannapieco, 2016; Few, 2013; Hevner et al., 2004).
The review follows Design Science Research principles (Hevner et al., 2004) and is informed by the DSR evaluation frameworks of Peffers et al. (2007) and Venable et al. (2016), which require that an artefact be grounded in kernel theories and evaluated for both technical rigour and practical utility. Rather than summarising each body of literature, the chapter interrogates what each contributes and what it leaves unresolved, so that the accumulated limitations justify the artefact described in Chapter 4. Sections 2.2 to 2.5 establish what quality means, how organisations attempt to manage it, why consistency matters in project cost management, and what tools and dashboards currently offer. Section 2.6 synthesises the limitations into a defended gap, and Section 2.7 derives eight design requirements.
2.2 Data Quality Dimensions
Data quality is the degree to which raw data conforms to characteristics that enable the solution of a given problem. It comprises attributes that satisfy the need translated into data creation: accuracy, completeness, reliability, and timeliness (Batini and Scannapieco, 2016). Accuracy refers to the extent to which values correctly represent the real-world phenomenon; completeness concerns the presence of required values; reliability concerns the credibility and dependability of information; and timeliness concerns fitness for decision-making at the required time (Wang and Strong, 1996; Batini and Scannapieco, 2016).
The present study adopts completeness, consistency, accuracy, and integrity as the operational dimensions most directly relevant to project cost records, drawing on the broader dimensions established by Wang and Strong (1996) and Batini and Scannapieco (2016). Table 2.1 summarises these four dimensions and their application in project cost management contexts.
Table 2.1: Data Quality Dimensions and Definitions (Wang and Strong, 1996)
Dimension	Definition	Source	Example in Project Cost Records
Completeness	The extent to which all required data values are present	Wang and Strong (1996); Batini and Scannapieco (2016)	Project cost records must include project identifier, WBS code, period date, and cumulative cost values
Consistency	The extent to which data values are uniform and free from format conflicts	Wang and Strong (1996); Ghasemaghaei and Calic (2019)	The same project identifier and WBS description must be used across all records
Accuracy	The extent to which data values correctly represent the real-world phenomenon	Wang and Strong (1996); Dong and Srivastava (2013)	Cumulative planned value, actual cost, and earned value must fall within legitimate ranges
Integrity	The extent to which data values satisfy inter-field logical constraints	Wang and Strong (1996); Project Management Institute (2021)	Cumulative values must not decrease over period index; dates must not precede baseline start
Two observations shape the argument that follows. First, the dimensions derive from different methodological traditions: Wang and Strong (1996) from a consumer-oriented study of what data users value, and Batini and Scannapieco (2016) from a systematic examination of technical approaches. This plurality reflects the multidimensional nature of data quality, but it also means that any study operationalising these dimensions must justify its specific choices. The present study adopts the four dimensions most consistently identified across both traditions and operationalises them into measurable metrics with explicit thresholds.
Second, and more consequentially, the dimensions are descriptive rather than prescriptive. They identify what quality means but do not specify how to enforce it continuously across operating modes. Neither source specifies the architectural mechanisms through which quality is enforced at the point of data entry, nor how identical validation logic might apply to batch and live data streams. This distinction between description and enforcement is the first building block of the gap: a framework that identifies what quality means but cannot enforce it continuously is incomplete wherever records arrive continuously, which is precisely the condition that characterises multi-project cost environments and motivates the diagnostic profiling of inconsistencies undertaken in this study.
2.3 Data Quality Frameworks
The Total Data Quality Management (TDQM) framework, developed within the MIT TDQM Program and formalised by Wang (1998), provides coherent strategies, policies, standards, and practices for maintaining data quality. It promotes preventive governance and documentation of quality-control plans that enable checking of accuracy, completeness, consistency, reliability, and timeliness across the data life cycle. Its strength lies in recognising that data quality is socio-technical: many initiatives fail not because tools are inadequate but because organisational culture does not support sustained attention to quality. The AIMQ methodology developed by Lee et al. (2002) demonstrates that these dimensions can be measured empirically in organisational settings, providing indirect support for TDQM's premise that quality is assessable and improvable through structured governance.
TDQM's limitation for this study is significant. It does not specify the technical mechanisms through which quality is enforced at the point of data entry, nor how identical validation logic might apply across batch and live streams. It assumes that quality is maintained through governance, training, and documentation rather than architectural enforcement. That assumption holds where data entry is a deliberate, controlled activity. In multi-project environments where cost records arrive continuously from multiple systems and contractors, governance alone cannot guarantee that every record conforms to the required contract.
The big data quality literature addresses volumes, varieties, and velocities of data. Cai and Zhu (2015) argue that traditional quality metrics require adaptation for volume, velocity, and variety, while Cichy and Rass (2019) survey data-quality frameworks and identify the need for systematic assessment and monitoring mechanisms. These approaches recognise that data is increasingly acquired from multiple sources and shared across platforms, and that automated techniques may be required to detect anomalies at scale. Their strength lies in their technical emphasis: traditional approaches designed for structured relational data may be insufficient for modern environments, and automated methods can identify patterns that manual rule-based systems miss.
However, these frameworks share two limitations for the present study. They are designed primarily for large-scale, high-velocity environments, whereas project cost data is moderate in volume, comprising 12,139 records over just under 109 consecutive weeks, and the primary concern is correctness and logical consistency rather than throughput. More importantly, neither specifies how validation rules should be enforced consistently across batch, incremental, and live modes. Both focus on assessment, cleansing, and detection, but do not address how identical validation logic applies when data arrives through different channels.
The comparison of TDQM and big-data-oriented approaches, as systematically reviewed by Batini et al. (2009), reveals a philosophical tension. TDQM treats data quality as a cultural and governance problem, while big-data approaches often treat it as a technical and computational problem. Neither approach alone provides a complete solution to enforcing consistent validation across batch, incremental, and live modes. TDQM supplies the conceptual framework but not the enforcement mechanism; big-data approaches supply technical capability but not the domain-specific precision required for project cost records. Organisations relying on governance alone may find that quality degrades when data entry is distributed across teams and systems. Organisations relying on technical cleansing alone may find that cleansing rules are not aligned with the definitions the business uses to make decisions. This unresolved tension is the second building block of the gap. It establishes that a new framework must combine the conceptual precision of TDQM with the technical enforcement offered by automated validation approaches, and extend both to cover live data streams.
2.4 Data Consistency in Project Cost Management
Data consistency maintains uniformity, accuracy, and credibility across systems and applications (Dong and Srivastava, 2013). It supports decision-making accuracy, operational efficiency, and compliance with regulatory and audit requirements (Ghasemaghaei and Calic, 2019; Janssen et al., 2017). In project cost management, cumulative planned value, actual cost, and earned value records form the backbone of earned-value management. The consequences of inconsistency in this domain are well documented empirically. Flyvbjerg et al. (2004), analysing 258 transport infrastructure projects, found that cost underestimation is a systematic rather than random phenomenon, with actual costs exceeding estimates in approximately 90% of projects. Love et al. (2010), examining rework in civil infrastructure, attributed a significant proportion of cost overruns to information quality failures rather than to construction or design errors. These studies establish that data quality defects in project controls are not merely administrative inconveniences but material contributors to cost overruns.
Any undetected anomaly, including negative cumulative values where invalid, actual cost recorded before the project start date, mismatched project identifiers, inconsistent WBS descriptions, or missing mandatory fields, can produce misleading cost variance and estimate-at-completion figures (Project Management Institute, 2021). Robust validation at the point of data entry or ingest is therefore essential, and in operational settings this means validation must be available not only in batch mode but also through a live endpoint that receives and validates records as they are submitted.
Established evidence must be distinguished from interpretation. The relationship between consistency and decision-making accuracy is well established (Project Management Institute, 2021; Flyvbjerg et al., 2004). The claim that consistency is associated with operational efficiency is supported by the broader data quality and decision-making literature (Dong and Srivastava, 2013; Ghasemaghaei and Calic, 2019), though the causal mechanism has not been fully demonstrated. The present study does not claim a causal relationship; it claims to enforce consistency through architectural means and measure the effect on detection completeness and cost variance reliability.
Organisations face significant challenges in achieving consistency. Data resides in various systems with different formats; data may contain inaccuracies, duplication, and outdated information; legacy systems pose integration challenges; and human entry introduces variation (Dong and Srivastava, 2013; Janssen et al., 2017). A more acute challenge is that validation is often performed only on static files. When records arrive continuously from external systems, malformed submissions may contain unexpected data types, missing fields, or out-of-bounds numerical inputs. Without a live endpoint connected to the validation engine, these records cannot be checked at the point of submission, and errors may remain undetected until the next batch cycle. In multi-project environments this delay is not neutral: a single malformed cumulative value can propagate into cost variance and estimate-at-completion calculations across the entire portfolio before the next reconciliation. No study identified in this review has demonstrated a solution that addresses both the static and the live dimensions of this challenge simultaneously.
Techniques for measuring consistency include data profiling, validation, and metrics such as completeness and uniqueness. Data profiling identifies rule violations and quality defects, while validation assesses conformity with predefined structural and logical constraints (Batini et al., 2009; Ehrlinger and Wöß, 2022). Quality measures such as completeness, uniqueness, and conformity may be used to assess improvement over time (Ghasemaghaei and Calic, 2019). Data-quality issues may be detected periodically or continuously, with alert mechanisms notifying stakeholders of non-conformity (Costa e Silva et al., 2024). The literature supports real-time detection as a concept but does not provide an implemented example in the project cost domain. This absence is the third building block of the gap and directly motivates the live API component evaluated under RQ3.
2.5 Tools, Dashboards and Framework Selection
2.5.1 Data Quality Measurement Tools: A Critical Reading
Commercial tools, including Informatica Data Quality, IBM InfoSphere QualityStage, and Talend Data Quality, perform data profiling, cleansing, monitoring, and reporting. These platforms are commonly positioned around enterprise-scale deployment, vendor support, governance integration, and infrastructure compatibility (Ehrlinger and Wöß, 2022). Open-source alternatives, including Pandera and Great Expectations, offer reproducibility, version control, configuration-driven design, and potential integration with application programming interfaces (Ehrlinger and Wöß, 2022; Bantilan, 2020).
Ehrlinger and Wöß (2022) provide a systematic comparison of data-quality tools and identify data profiling, quality measurement, and automated monitoring as three core functional areas. Their review indicates that commercial platforms more commonly package these capabilities within enterprise-oriented products, whereas open-source tools may require greater technical configuration but offer greater transparency and adaptability. This distinction supports the present study's emphasis on reproducible, configuration-driven validation rather than proprietary platform dependence.
A critical reading of the tool literature reveals an unacknowledged bias. The commercial literature emphasises enterprise features, scale, vendor support, and infrastructure integration, reflecting an assumption that quality is achieved through comprehensive platforms managed by specialists (Ehrlinger and Wöß, 2022). The open-source literature emphasises reproducibility, configurability, and community contribution, reflecting an assumption that quality is achieved through transparent, modular components that can be inspected and adapted (Bantilan, 2020; Ehrlinger and Wöß, 2022). For a research study, the second assumption is more defensible because it permits examination and replication. For an enterprise deployment, the first may be more defensible because it provides the support infrastructure large organisations require. The choice is therefore epistemological, not merely technical, and the present study grounds it in the requirements of research reproducibility rather than an unexamined preference.
The same critical lens applies within the open-source ecosystem. The choice between Pandera and Great Expectations carries substantive implications. Pandera is lightweight, integrates directly with Pandas dataframes and Python type hints, and supports declarative schema validation through column definitions, data-type constraints, nullability rules, uniqueness requirements, and custom checks (Bantilan, 2020; Pandera, 2026). Great Expectations is more extensive, provides verifiable assertions about data through expectation suites and data documentation, and integrates with multiple execution environments, but introduces dependencies that can complicate reproducibility (Great Expectations, 2026; Ehrlinger and Wöß, 2022). The present study uses Pandera for the primary data contract and Great Expectations for supplementary validation, exploiting the strengths of both while acknowledging that neither alone provides a complete solution. This nuance is absent from much of the literature, which tends to treat open-source tools as a homogeneous category.
A genuine conflict persists between commercial and open-source options. Commercial tools offer comprehensive functionality but carry licensing costs and may restrict adaptability to research contexts, whereas open-source tools offer reproducibility and configurability but may require greater technical expertise and lack vendor-supported scalability (Ehrlinger and Wöß, 2022). The present study's choice of open-source tools was deliberate, based on the need for reproducibility and configuration-driven design. Reproducibility is essential for a research artefact because it allows other researchers to verify the findings; a commercial tool would introduce licensing dependencies that make replication difficult.
Governance remains relevant because consistency is a collective as well as a technical achievement. Janssen et al. (2017) demonstrate that decision quality depends not only on analytical capability but also on governance arrangements, collaboration, and the quality of the underlying data. A technically sound validation engine may fail if the definitions it enforces are not agreed upon by the stakeholders who produce and consume the data. In project controls research, Python provides the practical substrate: Pandas and NumPy support data manipulation and matching; Plotly supports visualisation; Flask allows the same validation logic to be exposed through an API endpoint, enabling synchronous checking at the point of submission. For structured error reporting, the present study adopts RFC 9457 (Nottingham et al., 2023), which defines a standard machine-readable format for HTTP API error responses and directly underpins the structured error reporting requirement in Section 2.7.
2.5.2 Dashboards: Design Principles and Their Limits
Dashboards visualise and manage data-quality metrics, enhance stakeholder engagement, and facilitate informed decision-making. Design guidance emphasises clarity, usability, relevance, and accessibility (Few, 2013; Sarikaya et al., 2019). Personalisation customises the dashboard to user needs; colour schemes and typefaces support navigation; drill-downs and filters allow interaction; and accessibility ensures availability to a broader range of stakeholders (Few, 2013; Sarikaya et al., 2019). Sarikaya et al. (2019) further characterise dashboards as interfaces that consolidate information to support monitoring, awareness, and decision-making, while noting that their effectiveness depends on managing complexity and making interactive functions intelligible to users.
Dashboard evaluation research further indicates that effectiveness should be assessed across multiple dimensions, including task performance, interaction workflow, perceived engagement, potential utility, and system implementation (Zhuang et al., 2022). Usability-focused reviews similarly identify usefulness, operability, learnability, ease of use, suitability for tasks, situational awareness, satisfaction, interface quality, content quality, and system capability as recurring evaluation criteria (Abdolahi et al., 2023). These criteria are relevant to the present artefact because a dashboard that displays validation outcomes must support not only visual interpretation but also timely identification of defective records.
The literature presents these principles as established guidance but does not always subject them to empirical validation. Few (2013) derives the principles from design practice rather than controlled experiments. Sarikaya et al. (2019), in a systematic review of dashboard research, observe that many studies report design guidelines without controlled evaluation of whether those guidelines improve user outcomes. This distinction matters because the present study evaluates its dashboard through structured system testing rather than usability questionnaires. It therefore addresses the system-efficacy dimension identified by Zhuang et al. (2022), particularly whether the dashboard reliably presents validation outcomes, rather than claiming to validate user experience or behavioural impact.
A further critical observation is warranted. The design principles literature often treats the dashboard as a passive display of pre-computed metrics. It assumes that the underlying data has already been validated and that the dashboard's role is to communicate results. This assumption holds where validation is performed upstream. It does not hold where validation is performed within the dashboard pipeline or through a live endpoint that feeds the dashboard. In such contexts, the dashboard must not only display quality metrics but also communicate the outcome of validation in real time. The design principles do not address this requirement directly. This limitation shapes the multi-mode view design adopted in the implementation.
Implementation involves defining metrics, integrating data, monitoring, and reporting. Metrics must be linked with goals and encompass relevance, completeness, timeliness, and adherence to standards (Few, 2013; Sarikaya et al., 2019). Indicators should cover trends, deviations, and exceptions. Integration synchronises incompatible data formats and reduces conflict (Dong and Srivastava, 2013); in live mode, integration extends through the Flask API, allowing external systems to submit records directly for validation.
Real-time monitoring tracks quality indicators and compares them with thresholds; alerts notify stakeholders of critical matters (Costa e Silva et al., 2024). Technical challenges include data complexity, technological integration, change management, and resource acquisition (Sarikaya et al., 2019). Solutions include effective governance, advanced integration tools, staff support, and scalable architecture. A live API further standardises submission and reduces manual file handling.
Case studies demonstrate how organisations have adopted dashboards for organisational improvement and business strategy. However, the case-study literature is predominantly descriptive. Kourtit and Nijkamp (2018), for example, describe an experimental smart-city dashboard for Stockholm but report qualitative observations rather than controlled comparisons or quantitative evaluations of detection performance. This methodological weakness is addressed in the present study through structured system testing against a spreadsheet baseline.
2.5.3 Streamlit and Framework Alternatives: A Critical Evaluation
Streamlit and Dash provide robust frameworks for developing interactive dashboards. Streamlit allows Python users to create interactive web applications without extensive web-development expertise. Streamlit applications are structured around two components. The user interface creates the front end with input controls and output indicators, while server-side logic handles data processing through a reactive programming model (Streamlit, 2026). Based on reactive expressions, the interface updates according to user interaction or data alteration, enabling immediate feedback without a full-page refresh. Session State allows selected variables and widget values to persist across reruns within a user session, although it is not intended to persist after a server restart (Streamlit, 2026). Layout functions support sidebars, panels, tabs, and navigation, while container and column functions support more complex structural arrangements.
The literature presents Streamlit as a practical framework but does not subject it to comparative evaluation against Dash or other alternatives. A critical evaluation reveals specific trade-offs that the literature does not discuss. Streamlit prioritises rapid development over production-grade deployment. Its documentation describes Session State as session-specific and not persisted after a server restart, while authentication and role-based access control are not presented as core built-in application-management features (Streamlit, 2026). These limitations are acceptable for a research artefact intended for demonstration and evaluation, but would require additional engineering for enterprise deployment. Dash offers more control over the front end and supports more complex interactions but requires more boilerplate and a steeper learning curve. Shiny offers similar capabilities in the R ecosystem but would require cross-language integration in a Python-based pipeline. Tableau and Power BI offer mature visualisation but are proprietary and would undermine the reproducibility requirement. The choice of Streamlit is therefore not a claim of superiority but a deliberate trade-off in favour of development speed, Python compatibility, and reproducibility.
This selection reflects a common pattern in research artefact development, where framework choice is determined by alignment with the implementation language, development effort, and reproducibility requirements rather than by enterprise feature completeness alone (Hevner et al., 2004; Ehrlinger and Wöß, 2022). This trade-off is consistent with the research objectives and is acknowledged as a limitation of the artefact in Chapter 7.
2.6 Research Gap Identification
The literature reviewed in this chapter supports four conclusions. First, data quality is multidimensional, and completeness, consistency, accuracy, and integrity are well established (Wang and Strong, 1996; Batini and Scannapieco, 2016). However, the dimensions are descriptive rather than prescriptive: they identify what quality means but do not specify how to enforce it continuously across operating modes.
Second, data consistency is critical in project cost management, and undetected anomalies can produce misleading cost variance and estimate-at-completion figures (Project Management Institute, 2021; Flyvbjerg et al., 2004). However, the literature does not identify a framework that enforces consistency across both static and live data streams in project cost records.
Third, tools and methods exist for measuring data quality (Batini et al., 2009; Ehrlinger and Wöß, 2022). However, many are designed primarily for batch processing. The literature supports real-time detection as a concept (Costa e Silva et al., 2024), but does not provide an implemented example in the project cost domain.
Fourth, dashboard design principles are well established (Few, 2013; Sarikaya et al., 2019), and the literature stresses the importance of distinguishing historical exploratory views from live monitoring views. However, few applied studies operationalise this distinction in a way that connects a live validation engine to a dashboard interface.
Taken together, these conclusions reveal a genuine gap: the literature does not identify a framework in project controls that combines multi-mode validation across batch, incremental, and live submission channels with a unified data contract.
Three counter-arguments must be addressed before the gap can be accepted as genuine.
Objection one: streaming data-quality tools already exist. Amazon Deequ, Monte Carlo, Soda, and Kafka schema registries offer real-time data-quality validation. Why is the gap real?
Response: These tools are technically capable but designed primarily for generic data pipelines rather than project cost records. Deequ, as described by Schelter et al. (2018), provides a declarative API that combines common quality constraints with user-defined validation logic, and Amazon Web Services (2019) similarly describes it as a tool for calculating quality metrics and defining and verifying data-quality constraints. It can therefore express custom checks, including constraints on data distributions and record-level properties. However, its principal design emphasis is scalable verification of large datasets rather than a project-controls-specific data contract governing ordered cumulative cost records. None of these tools has been evaluated in the project controls literature against a spreadsheet baseline, and none has been integrated with a dashboard that displays validation outcomes in real time. The gap is therefore not the absence of any streaming validation tool but the absence of an integrated framework combining domain-specific logical validation, multi-mode consistency, live feedback, and empirical evaluation in project controls.
Objection two: validation is best performed upstream by data producers, so a live endpoint is unnecessary.
Response: Upstream validation is preferable where feasible, and the present study does not claim that live validation replaces it. It claims that live validation is a necessary complement when records arrive from multiple systems and contractors whose data quality cannot be guaranteed. The literature on multi-project environments documents exactly this scenario (Project Management Institute, 2021). A live endpoint provides a final line of defence at the point of ingest.
Objection three: the cost of implementing a live endpoint outweighs the benefit.
Response: The direct operational cost is negligible for the record volumes typical of project cost data, although this proposition is evaluated empirically in Chapters 5 and 6 rather than assumed here. Development and maintenance costs are real, and the study does not dismiss them: they are acknowledged in Chapter 7 as a practical limitation that must be weighed against the cost of undetected defects propagating into cost variance calculations. The benefit, detection of malformed records before they enter those calculations, is demonstrated through detection completeness results in Chapter 6.
Addressing these objections strengthens rather than weakens the gap. It shows that the gap is not the absence of any relevant technology but the absence of an integrated framework that combines domain-specific validation, multi-mode consistency, live feedback, and empirical evaluation. This gap justifies the present study's research design. Design Science Research (Hevner et al., 2004) is appropriate because the study constructs an artefact, a data-quality dashboard with a live API, to address a practical problem that the literature has identified but not solved. The artefact is evaluated through structured system testing (Myers et al., 2011) against traditional spreadsheet-based checks, using metrics such as detection completeness, latency, and technical reliability. The evaluation design follows the FEDS framework of Venable et al. (2016), which distinguishes between ex ante and ex post evaluation and between artificial and naturalistic settings. It is documented in Chapter 3 (Section 3.2.2) as ex post evaluation in an artificial setting, and operationalised in Chapter 5 as structured system testing.
The intellectual argument can now be stated explicitly. Data quality in project cost records has been treated as a batch-oriented, one-time activity. The dimensions are established, consistency is recognised, tools exist, and design principles are known. What is missing is a framework that enforces the same validation logic continuously across batch, incremental, and live modes, through a unified data contract and a live API endpoint, and that communicates the results through an interactive dashboard. This study designs, implements, and evaluates that framework.
2.7 Design Requirements Derived from Literature
The gap in Section 2.6 gives rise to eight design requirements. These requirements are not a flat list; they fall into four groups that reflect the layered structure of the artefact. Diagnostic requirements define what is measured. Architectural requirements define how the system enforces measurement across modes. Quality-attribute requirements define how the system presents and sustains its behaviour. Verification requirements define how correctness is demonstrated. Within each group, some requirements are essential to the artefact functioning at all, while others improve quality but are not strictly necessary. R-DQ1, R-DQ2, R-DQ3, and R-DQ4 are essential because, without them, the artefact cannot address the gap. R-DQ5, R-DQ6, R-DQ7, and R-DQ8 are quality-attribute and verification requirements that strengthen the artefact but could, in principle, be partially relaxed without invalidating the core contribution. This prioritisation directly informs the limitations discussed in Chapter 7.

Each is traceable to a gap or theoretical insight, and each is operationalised in a specific component of the system. They ensure that the artefact addresses the gap systematically, in accordance with Design Science Research principles (Hevner et al., 2004).
2.8 Summary
This chapter has reviewed four bodies of literature. The dimensions literature (Wang and Strong, 1996; Batini and Scannapieco, 2016) established four core dimensions but showed that they are descriptive rather than prescriptive. The frameworks literature (Wang, 1998; Batini et al., 2009; Cai and Zhu, 2015; Cichy and Rass, 2019) showed that neither governance-oriented nor big-data-oriented approaches specify how to enforce consistent validation across batch, incremental, and live modes. The consistency literature (Dong and Srivastava, 2013; Project Management Institute, 2021; Flyvbjerg et al., 2004) established why consistency matters but showed that the literature has not operationalised consistency enforcement across the full range of data arrival modes. The tools and dashboard literature (Few, 2013; Sarikaya et al., 2019; Ehrlinger and Wöß, 2022) established design principles but showed that few applied studies connect a live validation engine to a dashboard interface.
Together, these bodies of literature reveal a genuine gap: the absence of a framework in project controls that combines multi-mode validation across batch, incremental, and live API channels with a synchronous endpoint and a unified data contract. This gap was defended against three counter-arguments and shown to be real, consequential, and unresolved by existing streaming data-quality tools. The gap justifies the present study's research design and motivates the eight design requirements in Section 2.7. These requirements form the bridge between the literature and the implementation. Chapter 3 describes the research design that operationalises them, while Chapter 4 describes the implementation of the system that embodies them.

3.2 Research Approach: Design Science Research
3.2.1 Justification for DSR
Design Science Research was selected because the study constructs an artefact, namely a data quality dashboard with a live API, to address a practical problem that the literature has identified but not solved (Hevner et al., 2004). Second, the study constructs an artefact, and DSR is the paradigm designed for research that produces and evaluates artefacts. Third, DSR requires both technical quality (correct detection, reproducibility, performance) and practical utility (clear error signalling that supports remediation), which matches the dual focus of the study.

3.3 Data Source and Selection
3.3.1 Dataset Provenance and File Inventory
The study uses the publicly available Project Portfolio Dataset (gacevedob, 2022), obtained from Kaggle on 22 October 2026 and licensed under CC BY-SA 4.0. The source is not a single clean tabular file but a collection of Excel workbooks and templates. The repository contains 17 files: eight principal project workbooks, eight corresponding EDM workbooks, and one Microsoft Project template.
The study uses only the eight principal project workbooks. The eight EDM workbooks and the Microsoft Project template are excluded because they contain supplementary estimating, resource, and scheduling information rather than the time-phased cost and progress records required by the validation rules. The eight principal workbooks are listed, checksummed, and profiled in Appendix B. The dataset documentation describes the portfolio as comprising six primary projects; the eight principal workbooks include identifiers P01 through P06 together with P17 and P18, giving eight distinct project files.
The decision to use all eight principal workbooks is stated explicitly. Cross-project consistency rules, for example that a project identifier maps to a single project name or that a WBS code maps to a single description within a project, are tested more strongly when there are more projects to compare. Retaining P17 and P18 therefore increases the test surface for the consistency dimension without altering the validation logic. The two additional files are treated as supplementary cases and are identified as such in the data dictionary (Appendix B). The project count is therefore unambiguous: the study uses eight principal project workbooks, of which six are described as primary in the source documentation.
3.3.2 Dataset Structure and Views
The dataset is used at two analytical levels, and the terminology is fixed here. The two views are distinguished as follows.
The WBS-level view contains one row per work-breakdown-structure element per reporting period. It is the granularity at which cost records are captured and is the input to record-level validation rules. It contains 2,727 rows and 10 fields.
The project-period view contains one row per project per reporting period. It is an aggregation of leaf-level WBS records and is the input to cross-record validation rules and to portfolio-level analysis. It contains 76 rows and 8 fields.
Neither view is called "raw" or "cleaned", because those terms obscure the distinction between the original source workbooks (which are raw) and the two derived analytical views (which are structured). The source workbooks are the raw data; the WBS-level and project-period views are derived analytical tables.
The source documentation reports 12,139 time-phased actual cost records. The 2,727-row WBS-level view is the study's derived analytical table, in which source cost records are consolidated to one observation per WBS element per reporting period. The consolidation rule, number of source records read, number of records excluded, and number of WBS-level observations produced are recorded in the data-preparation log in Appendix B. The 76-row project-period view is in turn aggregated from the leaf-level WBS records, as justified in Section 3.3.4. Table 3.3 summarises the structure of the views.

3.3.3 Transformation from Source Workbooks to Analytical Views
The transformation from the source Excel workbooks to the two analytical views is a methodological step and is documented so that the reproducibility claim is demonstrable. First, each of the eight principal workbooks is read with pandas.read_excel, preserving the sheet layout defined by the source workbook. Column headers are normalised to lower snake case, and any whitespace is stripped. Second, the WBS code is coerced to a string to preserve leading zeros, because WBS codes such as 011 and 111 are distinct identifiers and must not be truncated to integers. Third, cumulative monetary columns (pv_cum, ac_cum, ev_cum) are coerced to float, and date columns are parsed with pandas.to_datetime(errors="coerce") so that malformed dates are surfaced as missing rather than silently accepted. Fourth, the eight per-workbook tables are concatenated into the WBS-level view.
Fifth, the project-period view is produced by aggregating the leaf-level WBS records only, as justified in Section 3.3.4.
Each transformation is logged. The log records the number of source cost records read from each workbook, the number of rows rejected by parsing, the number of leaf-level records retained, the number of parent-level records excluded, and the number of rows written to each analytical view. The log is the evidence for the row counts in Table 3.3. A sample is reproduced in Appendix B, and the full log is regenerated whenever the pipeline is run.
3.3.4 Aggregation Assumption and Leaf-Level Identification
Aggregating cumulative WBS values into a project-period view is the largest analytical risk in the study. If WBS structures contain parent and child elements, and if parent rows already aggregate child rows, then summing all records would double-count costs. This assumption is therefore stated explicitly and defended.
The aggregation assumes that WBS-level records represent mutually exclusive cost components. This assumption was verified for each principal workbook by inspecting the WBS hierarchy recorded in each source workbook.
Subordination was determined from the WBS hierarchy recorded in each source workbook. Where an explicit parent-child field was available, it was used directly. Where no explicit hierarchy field was available, the WBS code structure was used, with the hierarchy rule and any exceptions documented in Appendix B. A record was classified as a leaf-level work package where it had no subordinate WBS code within the same project and carried non-null cumulative monetary values. Where parent-level rows were present and empty, they were excluded from the aggregation. Only leaf-level records were summed into the project-period view.
The aggregation procedure is therefore: for each project and period, sum pv_cum, ac_cum, and ev_cum over leaf-level records only; compute progress_pct for the project-period record as revenue_claimed / max(pmb_budget) × 100, where revenue_claimed and pmb_budget are the cumulative earned value and cumulative planned value (PMB) of the aggregated project-period record, and max(pmb_budget) is the project's planned value at completion. The derived field names revenue_claimed and pmb_budget correspond to the source cumulative fields ev_cum and pv_cum; the mapping between source and derived field names is given in Chapter 4, Table 4.1. Finally, join the project-level attribute baseline_start_date. The progress_pct attribute is therefore a derived project-period attribute and is not present in the WBS-level source data. This procedure removes the double-counting risk that would otherwise invalidate the project-period results. The classification rule, the counts of leaf-level and parent-level records, and the number of parent-level records excluded from aggregation are reported in Appendix B.

The progress_pct attribute is derived as revenue_claimed / max(pmb_budget) × 100 (Section 3.3.4) and is not present in the WBS-level source data. The full field mapping between the WBS-level and project-period views is given in Chapter 4, Table 4.1.
3.3.6 Selection Justification
The dataset was selected for four reasons. First, it is publicly available and openly licensed, which supports reproducibility. Second, it contains multiple projects, which is essential for testing cross-project consistency rules. Third, it contains sufficient volume (12,139 time-phased actual cost records consolidated into 2,727 WBS-element-by-period observations over just under 109 consecutive weeks) to evaluate rule-level detection and batch-processing performance under controlled conditions. Fourth, it contains time-phased records, which is necessary for testing monotonicity and date-ordering constraints. The dataset's limitations are acknowledged in Chapter 7.
3.4 Operationalisation of Data Quality Dimensions
3.4.1 From Dimensions to Metrics
The four data quality dimensions identified in Chapter 2, namely completeness, consistency, accuracy, and integrity, are abstract. To be enforceable, they must be operationalised into measurable metrics with explicit formulas and target thresholds. The operationalisation follows the principle that a metric must be computable from the data contract and must produce a numeric score that can be compared against a threshold (Batini et al., 2009). The formulas are summarised in Table 3.5.
Table 3.5: Operationalisation of data quality metrics
Dimension	Operational definition	Formula	Target threshold
Completeness	Proportion of non-missing values in required fields	(Non-missing values ÷ Total values) × 100	≥ 98%
Consistency	Proportion of unique composite keys across records	(Unique keys ÷ Total values) × 100	≥ 99%
Accuracy	Proportion of values that conform to declared type and permitted domain	(Conforming values ÷ Total values) × 100	≥ 97%
Integrity	Proportion of records satisfying inter-field logical constraints	(Constraint-satisfying records ÷ Total records) × 100	≥ 99%
3.4.2 Justification for a Rule-Based Approach
The artefact uses a deterministic, rule-based validation approach rather than machine learning or statistical anomaly detection. Each validation rule is explicitly defined, configuration-driven, and traceable to a data quality dimension. This approach is appropriate because project cost control requires auditable decisions: a flagged record must be traceable to a specific rule, field, value, and remediation action. Machine learning methods were considered but not adopted because they typically require representative training data, may produce probabilistic outputs, and provide weaker explanatory transparency for rule-based cost-control constraints. The rule-based approach also supports the multi-mode consistency requirement directly: the same rule can be invoked identically in batch, incremental, and live API modes, whereas a probabilistic model would require additional checks to ensure its behaviour does not drift across modes.
3.4.3 Threshold Justification and Sensitivity Analysis
The thresholds are design decisions, not facts derived from a single source. They are informed by the operational context of project cost control and by the general data quality literature (Batini et al., 2009; Ehrlinger and Wöß, 2022), which establishes that threshold selection is context-dependent. The present study therefore states the thresholds explicitly as design decisions and tests their sensitivity in Chapter 5.
The rationale for each threshold is as follows. Completeness at 98% reflects the observation that a small margin of missing values may be tolerable in portfolio-level indicators, but larger gaps materially distort cost variance and forecasts. Consistency at 99% reflects the observation that duplicate keys and format conflicts are treated as errors because they undermine key uniqueness and cross-record traceability. Accuracy at 97% reflects the observation that numerical values may occasionally fall outside expected domains for legitimate reasons, but systematic non-conformity indicates data entry problems. Integrity at 99% reflects the observation that logical violations such as decreasing cumulative values are treated as integrity violations because they breach the expected monotonicity of cumulative values.
Sensitivity design. The study does not rely on a single operating point. Chapter 5 reports detection completeness and false positive rate at three thresholds per dimension: 95%, 98%, and 99% for all four dimensions. Using the same candidate thresholds across all dimensions is deliberate. It is simpler to present, easier to compare across dimensions, and removes any appearance that thresholds were chosen dimension-by-dimension to produce favourable results. The selected thresholds in Table 3.5 (98%, 99%, 97%, 99%) are then assessed against these alternatives in Chapter 5.
3.4.4 Rule-to-Dimension Mapping and Classification Basis
Each validation rule is mapped to one of the four dimensions. The mapping requires a precise definition of accuracy and integrity, because the two are sometimes conflated in applied data quality work. In this study, accuracy is defined narrowly: a value is accurate if it conforms to its declared data type and falls within the permitted domain for that field (Wang and Strong, 1996; Batini and Scannapieco, 2016). Integrity is defined as the extent to which a record satisfies inter-field and cross-record logical constraints that cannot be evaluated on a single field in isolation. The distinction is therefore between field-level conformance (accuracy) and relationship-level conformance (integrity).
This distinction resolves the apparent arbitrariness between R4 and R9. Rule R4 checks whether a cumulative value is negative, which is a field-level domain constraint, and therefore accuracy. Rule R9 checks whether a cumulative value decreases between adjacent periods, which is a relationship-level constraint that requires comparing two records, and therefore integrity. Table 3.6 states the mapping together with the classification basis.
Table 3.6: Rule-to-dimension mapping with classification basis
Rule	Description	Dimension	Classification basis
R1	Missing required fields	Completeness	Field presence
R2	Incorrect data types	Accuracy	Field-level type conformance
R3	Invalid period index	Accuracy	Field-level domain (≥ 1)
R4	Negative cumulative values	Accuracy	Field-level domain (≥ 0)
R5	Duplicate composite keys	Consistency	Key uniqueness
R6	Inconsistent project names	Consistency	Key-to-attribute uniformity
R7	Inconsistent WBS descriptions	Consistency	Key-to-attribute uniformity
R8	Out-of-order period dates	Integrity	Cross-record ordering
R9	Decreasing cumulative values	Integrity	Cross-record monotonicity

R12	Missing WBS description	Completeness	Field presence

3.6 Validity, Reliability, and Trustworthiness
3.6.1 Construct Validity
Construct validity concerns whether the metrics actually measure the dimensions they are intended to measure. The metrics are derived from established definitions (Wang and Strong, 1996; Batini and Scannapieco, 2016) and are operationalised with explicit formulas (Table 3.5). The accuracy and integrity constructs are defined narrowly and distinctively (Section 3.4.4) so that the mapping from rule to dimension is principled. Each rule is mapped to a dimension (Table 3.6), and the dimension scores are computed from rule violations.
3.6.2 Internal Validity and the Spreadsheet Baseline
Internal validity concerns whether the observed effects can be attributed to the artefact rather than to confounding factors. Two controls are used. First, the artefact applies the same validation logic across batch, incremental, and live API modes through a shared validation engine, and regression testing verifies that identical records produce identical flags regardless of entry mode. Second, the comparative evaluation against spreadsheet-based checks uses identical test sets, so any difference in detection performance can be attributed to the artefact rather than to differences in data.
Because the spreadsheet baseline is central to RQ3, it is defined rigorously. The baseline is a controlled, rule-equivalent manual checking protocol, not an ad hoc use of Excel. Specifically, the baseline implements the same 14 rules in spreadsheet formulas over the same test records. Each rule is reproduced as a column-level formula or, where a rule requires cross-record comparison, as a helper column that compares the current row with the previous row for the same WBS or project. The baseline produces a binary flag per rule per record. The same ground-truth labels are used for both the baseline and the artefact. Detection completeness is computed as the proportion of ground-truth defects that each method flags; false positive rate is computed as the proportion of clean records that each method flags. The baseline is therefore rule-equivalent to the artefact: it checks the same rules against the same data, and any difference in performance is attributable to how the rules are implemented and executed, not to which rules are checked. The baseline protocol and its formulas are reproduced in Appendix C.
3.6.3 Ground Truth Construction
Detection completeness and false positive rate both depend on ground truth, that is, on knowing which records are defective and which are not. The construction of ground truth is therefore specified here.
Ground truth comprises two strata. The first comprises naturally occurring rule violations that have been independently adjudicated. The second comprises synthetic defects injected into verified conforming records using a documented random seed. A separate clean evaluation set is used to estimate false positive rates. The same labelled test sets are used for the artefact and the spreadsheet baseline.
Adjudication of naturally occurring violations. Naturally occurring violations were identified through exhaustive evaluation of the 14 rules and then adjudicated against the source workbook, the relevant field definitions, and the project-level context. A record was retained as a ground-truth defect only where the violation could be independently confirmed. Records flagged by the validation engine but not confirmed during adjudication were classified as candidate false positives. They were retained in the clean evaluation set only where source verification, rule verification, and contextual review confirmed that no rule violation existed. The final clean evaluation set comprised 200 records verified as defect-free through this process. Ground-truth defects were therefore confirmed through independent adjudication against the source workbook, the written rule definition, and project-level context; validation flags alone were not treated as ground truth. The adjudication protocol is summarised in Table 3.8.
Table 3.8: Adjudication protocol for naturally occurring violations
Adjudication step	Decision rule
Initial flagging	All records evaluated against the 14 rules
Source verification	Flagged value checked against the original workbook cell or source sheet
Rule verification	Flag checked against the written rule definition
Contextual check	Legitimate edge cases, such as zero-cost periods, reviewed
Final classification	Confirmed defect, clean record, or unresolved case
Documentation	Adjudication decisions recorded in Appendix B
The number of adjudicated naturally occurring defects, disaggregated by rule and evaluation view, is reported in Appendix B.
Synthetic mutation protocol. Synthetic defects are injected into 400 verified conforming records drawn from the WBS-level and project-period views. One violation instance is created per injection, and no two violations overlap on the same record. For single-record rules, one violation instance corresponds to one mutated record. For paired-record rules, one violation instance corresponds to a minimal pair of records, namely one baseline record and one altered record. The 280 synthetic defects therefore comprise 280 violation instances. Of the 400 records in the mutation set, 380 are consumed (180 for single-record rules and 200 for paired-record rules), and 20 remain unused. A separate set of 200 records, verified as defect-free through full adjudication, is used exclusively to estimate false positive rate. Detection completeness is calculated over the adjudicated naturally occurring defect set and the synthetic violation set. The random seed is 42. 3.6.4 Evaluation Metrics
Detection completeness, false positive rate, precision, and latency are defined formally before Chapter 5. The three-detection metrics are computed against the ground truth constructed in Section 3.6.3 and are used in the success criteria in Section 3.6.5.
Detection completeness (also referred to in the literature as recall or sensitivity) measures the proportion of defective records that the validation engine correctly flags:
"Detection completeness" = TP / (TP + FN)
False positive rate measures the proportion of clean records that the validation engine incorrectly flags:
"False positive rate" = FP / (FP + TN)
Where, for each rule:
Table 3.11: Confusion matrix components
Symbol	Definition
TP (true positive)	A defective record correctly flagged
FN (false negative)	A defective record not flagged
FP (false positive)	A clean record incorrectly flagged
TN (true negative)	A clean record correctly not flagged
Precision is also reported, defined as:
"Precision" = TP / (TP + FP)
Precision is included as a supplementary measure because it combines detection performance and false-positive performance in a single figure. A system that flags every record as defective would achieve 100% detection completeness but would have low precision and a high false positive rate. Reporting precision alongside the two primary metrics therefore guards against over-flagging.
The metrics are first computed per rule, so that performance can be inspected for each of the 14 rules individually, and are then aggregated across rules for the success criteria in Section 3.6.5. Aggregation uses micro-averaging: TP, FN, FP, and TN are summed across rules before the metric is computed. This choice is deliberate. Micro-averaging weights each rule by the volume of records to which it applies, so the aggregate metric reflects the validation workload as a whole rather than the unweighted average of 14 equally weighted rule-level scores. Per-rule metrics are reported in Chapter 5.
Latency is defined as the wall-clock time from the moment an HTTP request is received by the Flask API to the moment the JSON response is returned. It includes JSON deserialisation, validation, and response serialisation, but not dashboard rendering, which is measured separately for the Streamlit dashboard. Latency is measured on the hardware and with the batch sizes and repetitions specified in Table 3.12.
Table 3.12: Latency measurement conditions

3.6.6 Reliability
Reliability concerns whether the study would produce the same results if repeated. The study supports reliability through configuration-driven rules, version control, and identical behaviour across environments. The validation rules are defined in configuration files rather than hard-coded, so the same rules apply in every environment. The test suite is automated and can be re-run by other researchers. The data-preparation pipeline described in Section 3.3.3 regenerates the analytical views from the source workbooks, so the row counts and derived tables are reproducible. The use of a publicly available and openly licensed dataset further supports reliability.
3.6.7 External Validity
External validity concerns whether the findings generalise beyond the specific dataset and context. The study is bounded by the dataset and by the scope of a master's dissertation. It does not claim universal generalisability. It claims that the framework is replicable and that the design principles, namely a shared validation engine, a unified data contract, and a live API, are transferable to other project cost environments. The limitations, including the single-portfolio dataset and the discrepancy between documented and available project counts, are discussed in Chapter 7.

3.6.8 Impact Quantification of Detected Inconsistencies
Objective 2 requires the study to quantify the impact of detected inconsistencies on cost variance, estimate accuracy, and portfolio-level forecasting reliability. Three impact measures are defined and reported in Chapter 6 alongside the profiling results (RQ1) and comparative results (RQ3).
Cost variance impact. For each project-period record, cost variance is computed as CV = EV − AC using cumulative values (Project Management Institute, 2021). The CV computed over the full dataset is compared with the CV computed over the clean subset (records with no findings). The difference, in absolute and percentage terms, quantifies the distortion in cost variance attributable to flagged records. The comparison is reported at project and portfolio levels.
Estimate accuracy impact. Estimate at Completion (EAC) is computed as EAC = BAC / CPI, where BAC is the project's budget at completion and CPI = EV / AC (Project Management Institute, 2021). The EAC computed over the full dataset is compared with the EAC computed over the clean subset. The difference quantifies the distortion in the estimate attributable to flagged records.
Portfolio forecasting reliability impact. Portfolio-level aggregates — total cost variance, total EAC, and the number of projects with negative cost variance — are computed for the full dataset and for the clean subset. The difference in each aggregate quantifies the extent to which undetected inconsistencies distort portfolio-level forecasts.
These impact measures are descriptive: they report the difference between indicators computed from the full dataset and those computed from verified-clean records. They do not claim causal attribution, and the difference is not interpreted as the sole effect of data quality defects. The measures are reported in Chapter 6 as supporting evidence for Objective 2 and as context for the comparative results in RQ3.

4.3 Data Ingestion and Cleaning
Before data can be validated against the formal contract, it must be ingested from the raw Kaggle Excel workbooks and normalised. This layer performs three critical functions: standardising column headers to snake_case, coercing string-based dates into Python datetime objects, and ensuring WBS codes are treated as strings to prevent the truncation of leading zeros. It also filters to leaf-level records (Section 3.3.4) so that parent-level rows are not double-counted in project-period aggregation.
Code Block 4.1: Data Ingestion and Cleaning Implementation (clean.py)
def build_project_totals(long_df):
"""
Collapse the leaf-level WBS EVM time-phase to one cumulative row per project
and period. Leaf-level filtering ensures parent-level rows (which already
aggregate children) are excluded, preventing double-counting (Section 3.3.4
of Chapter 3).
"""
missing = REQUIRED_SOURCE_COLUMNS - set(long_df.columns)
if missing:
raise ValueError(
"source data is missing required column(s): " + ", ".join(sorted(missing))
)

work = long_df.copy()
work["project_id"] = work["project_id"].astype(str).str.strip()
work["period_date"] = pd.to_datetime(work["period_date"], errors="coerce")

# --- Leaf-level filter (Section 3.3.4) ---
# A leaf-level record has no subordinate WBS code and carries non-null
# cumulative monetary values. Parent-level rows (where present) are excluded.
has_children = work.groupby("project_id")["wbs_code"].transform(
lambda s: s.apply(lambda c: any(
other != c and other.startswith(str(c) + ".") for other in s
))
)
work = work[~has_children]
# Parent-level rows with empty cumulative values are also excluded.
work = work.dropna(subset=["pv_cum", "ac_cum", "ev_cum"])

for column in ("pv_cum", "ac_cum", "ev_cum"):
work[column] = pd.to_numeric(work[column], errors="coerce").fillna(0.0)

work = work[work["project_id"].ne("") & work["period_date"].notna()]

# Sum LEAF-LEVEL cumulative values only.
totals = (
work.groupby(["project_id", "period_date"], as_index=False)[["pv_cum", "ac_cum", "ev_cum"]]
.sum()
.sort_values(["project_id", "period_date"])
.reset_index(drop=True)
)
totals.attrs["leaf_records"] = len(work)
totals.attrs["dropped_rows"] = len(long_df) - len(work)
return totals


def transform_to_contract(long_df, time_period_prefix=TIME_PERIOD_PREFIX, round_to=ROUND_TO):
"""
Transform leaf-level cumulative EVM data into the derived data contract.

The derived contract stores CUMULATIVE values so that Rule R9
(cumulative monotonicity) can be applied on the project-period view,
consistent with Chapter 3 Table 3.6 and Table 3.9. Period movements are
computed separately by the dashboard for visualisation when needed.
"""
report = CleaningReport(source_records=len(long_df))
if long_df.empty:
raise ValueError("source data is empty - run download_kaggle_data.py first")

totals = build_project_totals(long_df)
report.dropped_rows = totals.attrs.get("dropped_rows", 0)
if totals.empty:
raise ValueError("no usable project/period combinations in the source data")

frames = []
for project_id, group in totals.groupby("project_id", sort=True):
group = group.sort_values("period_date").reset_index(drop=True)
period_index = pd.Series(range(1, len(group) + 1), index=group.index)

# Cumulative values are stored directly (not de-cumulativised) so that
# R9 can check cumulative monotonicity on the project-period view.
pmb_budget = pd.to_numeric(group["pv_cum"], errors="coerce").fillna(0.0).clip(lower=0.0)
actual_cost = pd.to_numeric(group["ac_cum"], errors="coerce").fillna(0.0).clip(lower=0.0)
revenue_claimed = pd.to_numeric(group["ev_cum"], errors="coerce").fillna(0.0).clip(lower=0.0)

baseline = float(pmb_budget.max())
report.baselines[project_id] = round(baseline, round_to)

if baseline > 0:
progress_raw = revenue_claimed.to_numpy(dtype=float) / baseline * 100.0
else:
progress_raw = revenue_claimed.to_numpy(dtype=float) * 0.0
report.progress_clipped += int(((progress_raw < 0) | (progress_raw > 100)).sum())

frames.append(
pd.DataFrame(
{
"project_id": project_id,
"time_period": [f"{time_period_prefix}{n}" for n in period_index],
"pmb_budget": pmb_budget.to_numpy(dtype=float),
"actual_cost": actual_cost.to_numpy(dtype=float),
"progress_pct": progress_raw,
"revenue_claimed": revenue_claimed.to_numpy(dtype=float),
"actual_date": group["period_date"].to_numpy(),
"baseline_start_date": group["period_date"].iloc[0],
}
)
)

cleaned = pd.concat(frames, ignore_index=True)
cleaned = cleaned.sort_values(["project_id", "time_period"]).reset_index(drop=True)

for column in ("pmb_budget", "actual_cost", "revenue_claimed"):
cleaned[column] = cleaned[column].clip(lower=0.0)
cleaned["progress_pct"] = cleaned["progress_pct"].clip(0.0, 100.0)

for column in ("pmb_budget", "actual_cost", "progress_pct", "revenue_claimed"):
cleaned[column] = cleaned[column].round(round_to)

cleaned["actual_date"] = pd.to_datetime(cleaned["actual_date"])
cleaned["baseline_start_date"] = pd.to_datetime(cleaned["baseline_start_date"])

return cleaned, report
De-cumulativisation for display. The de_cumulativise helper is retained and used only by the dashboard, not by the validation pipeline. The dashboard displays period movements for chart readability, computing them on the fly from the stored cumulative values. Because the validation engine consumes the cumulative values, Rule R9 (cumulative monotonicity) operates on the correct semantics, consistent with Chapter 3 Table 3.6 and Table 3.9. The CleaningReport.negative_diffs counter still tracks any negative movements detected during dashboard-side de-cumulativisation, but no de-cumulativisation occurs on the validation path.

4.5 Validation Rules (R1–R14)
The validation rules are covered by a 215-test Pytest suite, implemented using Pytest's fixture and parametrisation mechanisms to support reusable validation scenarios (pytest, 2026). The suite comprises rule-level tests, boundary tests, and regression tests, consistent with established software-testing principles (Myers et al., 2011).
Evaluation view. Consistent with Chapter 3 Table 3.9, rules R1–R7, R10, R11, and R12 are evaluated on the WBS-level view; rules R8, R9, R13, and R14 are evaluated on the project-period view. R6 and R7 are cross-record rules (grouping by project_id and by project_id + wbs_code respectively), so they are implemented in cross_record_rules.py even though they operate on WBS-level data.
Severity justification. Severity is High where the defect prevents meaningful validation (R1, R2, R12 — structural failures) or directly corrupts cumulative variance (R8, R9 — chronological and monotonicity violations); Medium otherwise. Severity orders findings for display; it does not by itself determine the HTTP outcome. Rejection (422) is reserved for the structural failures (R1, R2, R12); every other finding, including the High-severity domain rules R8 and R9, is quarantined (202). This is the classification implemented in §4.6 and summarised in Table 4.4.
Note on code blocks: Code Blocks 4.4 and 4.5 show representative implementations of R1 (record-level) and R9 (cross-record). The remaining rules (R2–R8, R10–R14) follow the same functional pattern: each accepts a DataFrame and returns a list of Finding objects, and all are available in the repository under data_quality/engine/.

Rule Definitions (R13, R14):
R13 (Budget Overrun): Compares the cumulative actual cost against the cumulative planned budget derived from the PMB. A record is flagged when cumulative actual cost exceeds a configurable multiple (default 3×) of the cumulative planned budget.
R14 (Spend vs Progress): Compares the cumulative spend ratio (actual_cost / pmb_budget) against the reported progress percentage. A record is flagged when actual_cost exceeds pmb_budget × (progress_pct / 100) × 1.20 — i.e., when cumulative spend exceeds the expected spend by more than a 20% tolerance. The tolerance (default 20%) is configurable via the YAML configuration file (§4.8.1).

"""R8: period_date must increase with period_index. Evaluated on project-period view."""

for (pid,), group in df.groupby(["project_id"]):

for i in range(1, len(group)):

def rule_r9_cumulative_monotonicity(df, key_columns, cumulative_columns):
"""R9: cumulative values must not decrease over period_index. Evaluated on project-period view."""
findings = []
for pid, group in df.groupby("project_id"):
group = group.sort_values("time_period")
for column in cumulative_columns:
if column in group.columns:
for i in range(1, len(group)):
current = group.iloc[i]
previous = group.iloc[i - 1]
if pd.notna(current[column]) and pd.notna(previous[column]):
if current[column] < previous[column]:
findings.append(_finding("R9", record_key(current, key_columns), column,
f"{column} decreased from {previous[column]} to {current[column]}",
f"Correct {column} to maintain monotonic increase"))
return findings

"""R10: period_date must fall within the project reporting window. Operates on WBS-level data."""

def rule_r13_budget_overrun(df, key_columns, multiplier=3.0):
"""R13: cumulative actual cost must stay within 3× cumulative budget."""
findings = []
for _, row in df.iterrows():
if all(c in df.columns for c in ["actual_cost", "pmb_budget"]):
actual = row["actual_cost"]
budget = row["pmb_budget"]
if pd.notna(actual) and pd.notna(budget) and budget > 0:
if actual > budget * multiplier:
findings.append(_finding("R13", record_key(row, key_columns), "actual_cost",
f"Cumulative actual cost {actual} exceeds {multiplier}× cumulative budget {budget}",
"Review cost allocation against the PMB"))

def rule_r14_progress_mismatch(df, key_columns, tolerance=0.20):
"""R14: cumulative spend must not outrun reported progress. Default tolerance 20%."""
findings = []
for _, row in df.iterrows():
if all(c in df.columns for c in ["actual_cost", "pmb_budget", "progress_pct"]):
actual = row["actual_cost"]
budget = row["pmb_budget"]
progress = row["progress_pct"]
if pd.notna(actual) and pd.notna(budget) and pd.notna(progress):
expected_max_spend = budget * (progress / 100)
if actual > expected_max_spend * (1 + tolerance):
findings.append(_finding("R14", record_key(row, key_columns), "actual_cost",
f"Actual cost {actual} exceeds expected spend {expected_max_spend:.2f} for {progress}% progress (tolerance {tolerance*100:.0f}%)",
"Review cost allocation or progress reporting"))
return findings

4.6 Live Flask API Implementation
The Flask API exposes the validation engine to external systems through four deliberately separated endpoints: POST /validate validates a record or batch, GET /status returns validation counters, GET /flagged returns the flagged-records log, and GET /health provides a liveness probe. Querying endpoints do not mutate validation state. The API supports both individual records and batches, applies severity-based outcome classification, and returns RFC 9457 problem-details responses for validation failures (Nottingham et al., 2023).
Rejection vs quarantine. A record is rejected where a structural defect prevents meaningful validation, specifically a missing required field (R1), an unexpected data type (R2), or a missing WBS description (R12). Such submissions return 422 Unprocessable Entity. A record with a domain-specific anomaly (out-of-bounds value, chronological inconsistency, budget overrun, progress mismatch) is quarantined for review and returns 202 Accepted. Both rejected and quarantined records are written to the same in-memory flagged-records log (retrievable via GET /flagged); the distinction is the HTTP response code and whether the record can be accepted for downstream processing.
Table 4.4: Runtime error handling for live API submissions
Outcome	Detection point	HTTP response	Handling action
Clean record or batch	No findings	200 OK	Accept submission
Missing required field	R1	422 Unprocessable Entity	Reject submission
Unexpected data type	R2	422 Unprocessable Entity	Reject submission
Missing WBS description	R12	422 Unprocessable Entity	Reject submission
Out-of-bounds value	R3 or R4	202 Accepted	Quarantine record and return findings
Logical or chronological anomaly	R5 to R11	202 Accepted	Quarantine record and return findings
Budget or progress anomaly	R13 or R14	202 Accepted	Quarantine record and return findings
Malformed JSON or payload	Request parsing	422 Unprocessable Entity	Reject submission
Batch classification policy. Outcomes are assessed per submission, not per individual record. The _classify() function determines the outcome for the entire batch based on the most severe finding across all records. The response body reports valid_records and invalid_records as record-level counts, but the HTTP status code and outcome label apply to the submission as a whole. This all-or-nothing policy is a deliberate deployment design choice: a batch containing any structural failure is rejected in its entirety, and a batch containing any domain anomaly is quarantined in its entirety.
Evaluation note. The comparative evaluation in Chapter 5 does not use the API's batch-level HTTP classification. Instead, Chapter 5 uses the Validator.validate() method directly to obtain per-record findings, so detection completeness and false positive rate are computed per record. The API's batch policy is a deployment feature; the evaluation uses the per-record findings that drive it.
Where a submission generates multiple findings, the API reports the most severe outcome and includes RFC 9457 problem-details fields identifying the governing rule, its machine-readable error type, and the affected record key. RFC 9457 permits extension members such as rule and record_key alongside its standard type, title, status, detail, and instance fields (Nottingham et al., 2023).

4.8 Multi-Mode Consistency Implementation
Multi-mode consistency is achieved by sharing the same Validator instance across all three modes: batch, incremental, and live API. The dashboard imports the Validator directly; the API exposes the same Validator via HTTP; batch and incremental orchestration both call Validator.validate().
The Validator gates each rule to its designated evaluation view (Chapter 3 Table 3.9). WBS-level rules (R1–R7, R10, R11, R12) run only when tier == "raw"; project-period rules (R8, R9, R13, R14) run only when tier == "derived". This gating is what enforces the rule-to-tier assignment in Table 3.9 at runtime and prevents rules from running against columns that are absent from their non-applicable tier.

key_columns = self.raw_key
cumulative_columns = RAW_CUMULATIVE_COLUMNS
else:

key_columns = self.derived_key

# WBS-level rules (Chapter 3 Table 3.9): R1-R7, R10, R11, R12.
# These rules expect the 10-field WBS-level contract. They must not

# ------------------------------------------------------------------

findings.extend(rule_r3_period_index(df, key_columns))

findings.extend(rule_r12_wbs_description_present(df, key_columns))

4.9 Implementation Challenges and Solutions
The DSR process is inherently iterative (Peffers et al., 2007). The implementation phase surfaced six specific technical challenges, each of which required a design alteration to satisfy the DSR requirements of technical rigour and reproducibility. These challenges are documented as refinements that emerged during the cycle, as anticipated in Chapter 3 §3.2.1.
Challenge 1: Divergence between batch and API data contracts
•	Expected behaviour: Same validation logic in both modes.
•	Observed behaviour: Batch contract included period_date monotonicity check; API contract did not.
•	Resolution: Extracted the contract into a single shared Validator module and imported it in all modes (batch, incremental, API, dashboard).
•	Learning: A single source of truth for the contract eliminates divergence.
Challenge 2: Excel date parsing produced type errors
•	Expected behaviour: Dates read as datetime objects.
•	Observed behaviour: Excel serial numbers read as integers, causing datetime type check failures.
•	Resolution: Added explicit pd.to_datetime conversion with errors="coerce" in the ingestion layer.
•	Learning: Ingestion is a defensive process; must not assume on-disk representation matches in-memory representation.
Challenge 3: Monotonicity checks produced false positives
•	Expected behaviour: Detect actual decreases in cumulative values.
•	Observed behaviour: Records appeared to decrease when merely out of order.
•	Resolution: Added group.sort_values("time_period") before monotonicity check.
•	Learning: Logical constraints involving sequences require data to be in sequence order before evaluation.
Challenge 4: Dashboard performance degraded on full dataset
•	Expected behaviour: Responsive user interface.
•	Observed behaviour: Recomputation on every interaction took several seconds on 12,139 records.
•	Resolution: Applied Streamlit's @st.cache_data decorator to data loading and metric computation functions.
•	Learning: Interactive dashboards require explicit caching strategy; without it, responsiveness degrades non-linearly with data volume.
Cache invalidation is based on the uploaded file identity and contents, ensuring that a revised upload triggers recomputation rather than returning a stale result.
Challenge 5: Dashboard used legacy pipeline, not shared Validator
•	Expected behaviour: Dashboard consumes the same Validator as the API (multi-mode consistency, R-DQ2).
•	Observed behaviour: Dashboard initially imported data_quality.legacy.pipeline.DataPipeline, which used a separate rule set.
•	Resolution: Migrated app.py to import data_quality.engine.validator.Validator. The legacy module is retained for reference only and is no longer used by the dashboard or API.
•	Learning: Multi-mode consistency is an architectural property that must be actively maintained; wrapping validation in a shared class is not sufficient if the dashboard bypasses it.
Challenge 6: Cumulative values lost in de-cumulativisation
•	Expected behaviour: R9 checks cumulative monotonicity on the project-period view (Chapter 3 Table 3.6 and Table 3.9).
•	Observed behaviour: de_cumulativise() converted cumulative values to period movements before storing them, so R9 was checking period-movement monotonicity, not cumulative monotonicity.
•	Resolution: Changed the derived contract to store cumulative values directly (pmb_budget, actual_cost, revenue_claimed are cumulative). Period movements are computed on the fly by the dashboard for chart readability, but validation operates on cumulative semantics.
•	Learning: De-cumulativisation is a display concern, not a validation concern; conflating the two changes the meaning of the rules being validated.
Challenge 7: Rules were not gated by tier, causing runtime errors on derived tier
•	Expected behaviour: WBS-level rules (R1–R7, R10–R12) run only on the WBS-level view; project-period rules (R8, R9, R13, R14) run only on the project-period view, per Chapter 3 Table 3.9.
•	Observed behaviour: All rules ran regardless of tier. When tier == "derived", R6 (project_name), R7 (wbs_code, wbs_description), and R10 (period_date) attempted to access columns absent from the 8-field derived contract, causing KeyError.
•	Resolution: Wrapped the WBS-level rules in if tier == "raw": and the project-period rules in if tier == "derived":, so each rule runs only against its designated evaluation view.
•	Learning: Evaluation-view assignment is not merely documentation; it must be enforced at runtime to prevent rules from operating on incompatible schemas.
Challenge 8: Dashboard thresholds were hardcoded, diverging from the config-driven rule engine
•	Expected behaviour: Thresholds are loaded from YAML (R-DQ6, §4.8.1), so changing a YAML value updates both the rule engine and the dashboard display consistently.
•	Observed behaviour: The Metric Table displayed hardcoded target values ([97, 98, 99, 99]), so a YAML threshold change would not update the dashboard's pass/fail colouring.
•	Resolution: The dashboard now calls load_config()["thresholds"] and uses those values for the Target column and Status evaluation, matching the rule engine's source of truth.
•	Learning: Configuration-driven design is only achieved if every consumer of the configuration actually reads it; partial loading creates silent divergence between engine and display.

6.7 Impact Quantification of Detected Inconsistencies (Objective 2)
Chapter 3, §3.6.8 defines three impact measures that quantify how detected inconsistencies affect cost variance, estimate accuracy, and portfolio-level forecasting reliability. These measures are reported here as supporting evidence for Objective 2 and as context for the comparative results in §6.8.

Methodology. For each measure, indicators are computed twice: once over the full dataset (all 76 records), and once over the clean subset (records with no findings, 59 records). The difference between the two quantifies the distortion attributable to the 17 flagged records. These are descriptive measures; they do not claim causal attribution, and the difference is not interpreted as the sole effect of data quality defects.

6.8 Comparative Results: Dashboard vs Spreadsheet-Based Checks (RQ3)
This section reports the comparative evaluation against the rule-equivalent spreadsheet baseline defined in Chapter 3, §3.6.2 and Appendix C. Two aspects of this comparison distinguish it from the detection completeness evaluation in Chapter 5, §5.8:

Test set. Chapter 5's detection completeness evaluation uses the 400-record mutation set with 280 synthetic defects (Chapter 3, Table 3.10). This comparative evaluation uses a separate, smaller test set of 77 records carrying 13 labelled defects, derived from the 76 project-period records plus one duplicate. The smaller size is appropriate because the spreadsheet baseline is evaluated manually (or via spreadsheet formulas), and 77 records × 13 defects × 14 rules is the largest set that can be adjudicated reliably within the study's scope. The two evaluations answer different questions: Chapter 5's asks "how completely does the artefact detect synthetic defects?", §6.8 asks "how does the artefact compare to a rule-equivalent spreadsheet on a real-data test set?"

Detection completeness and false positive rate are evaluated at three candidate thresholds per dimension: 95%, 98%, and 99%. Rationale for selected thresholds (as established in Chapter 3, §3.4.3):

Completeness at 98%: A small margin of missing values may be tolerable in portfolio-level indicators, but larger gaps materially distort cost variance and forecasts.
Consistency at 99%: Duplicate keys and format conflicts are treated as errors because they undermine key uniqueness and cross-record traceability.
Accuracy at 97%: Numerical values may occasionally fall outside expected domains for legitimate reasons, but systematic non-conformity indicates data entry problems.
Integrity at 99%: Logical violations such as decreasing cumulative values are treated as integrity violations because they breach the expected monotonicity of cumulative values.
CHAPTER 7: CONCLUSIONS
7.1 Answers to Research Questions
RQ1: What data quality inconsistencies exist in budget and actual cost records, and how can they be systematically profiled across completeness, consistency, accuracy, and integrity dimensions?

Answer: The profiling identified 17 logical anomalies (22.37% of the dataset) across 7 projects, with Project P06 being the most affected. The four data quality dimensions were operationalised into measurable metrics (Chapter 3, Table 3.5), with the derived tier achieving 95.53% overall quality (completeness 100%, consistency 100%, accuracy 100%, integrity 77.63%). The systematic profiling across all four dimensions captures different aspects of data quality that a single composite score would obscure. The impact quantification (Chapter 6, §6.7) further shows that these 17 flagged records distort project-level cost variance by up to 48.11% (P06) and project-level EAC by up to 0.46% (P06), while their portfolio-level effect is smaller (0.96% for CV, 0.23% for EAC) due to concentration in two projects (P06, P18). This confirms that the flagged records are not benign outliers but genuine data quality defects whose correction changes the project's apparent financial position.

RQ2: How can an interactive Python dashboard with a live Flask API endpoint be designed to visualise, validate, and support improvement of data quality across batch, incremental, and live API modes?

Answer: The dashboard enforces a unified data contract across batch, incremental, and live API modes through a shared Validator (Chapter 4, §4.8). The regression test confirmed 100% multi-mode consistency across 500 sample records (Chapter 5, §5.6). The live API validates incoming records synchronously with response times under 2 seconds (Chapter 6, §6.12). The shared-contract architecture, combined with per-tier rule gating that enforces Chapter 3, Table 3.9 at runtime, is the key design decision that makes multi-mode consistency possible. The dashboard's use of the shared Validator (rather than a separate legacy pipeline) ensures that visualisations reflect the same validation logic that the API returns.

RQ3: How effective is the dashboard compared with traditional spreadsheet-based quality checks under batch, incremental, and live API submission conditions?

Answer: The dashboard achieves 100% detection completeness compared to 92.31% for spreadsheet-based checks, with the improvement being most pronounced for logical anomalies (+33.33 percentage points). The dashboard also provides 100% attribution of defects to specific records compared to 76.92% for spreadsheets. The dashboard is faster (0.059s vs 0.142s on 77 records) and supports all three modes (batch, incremental, and live API), which spreadsheet-based checks do not support. The comparative evaluation (Chapter 6, §6.8) uses per-record Validator findings, matching the unit of analysis of the spreadsheet baseline.

7.2 Contributions to Knowledge
Empirical evidence on live API validation: The finding that multi-mode consistency reaches 100% through a shared-contract architecture has not been reported in the project controls literature. This represents a contribution to design knowledge on how validation logic can be enforced consistently across batch, incremental, and live modes in project cost contexts. The tier-gated rule execution (Chapter 4, Code Block 4.8) is a specific architectural pattern that prevents rules from running against incompatible schemas — a form of architectural enforcement that the literature does not currently describe.

Controlled comparison methodology: The comparison against spreadsheet-based checks is statistically grounded, with quantitative evidence for the claim that spreadsheet-based checks are labour-intensive and incomplete, particularly for logical anomalies that require inter-field reasoning. The comparative evaluation uses a rule-equivalent baseline (same 14 rules, same test records), ensuring that any performance difference is attributable to implementation and execution rather than to rule selection.

Operationalisation of data quality dimensions: The operationalisation is simple, reproducible, and directly aligned with the theoretical dimensions established by Wang and Strong (1996) and Batini and Scannapieco (2016). The explicit thresholds (98/99/97/99), sensitivity analysis (Chapter 6, §6.13), and rule-to-dimension mapping (Chapter 3, Table 3.6) provide a replicable foundation for future research in other project cost environments.

Impact quantification of detected inconsistencies: Chapter 6, §6.7 introduces three impact measures — cost variance impact, estimate accuracy impact, and portfolio forecasting reliability impact — that operationalise Objective 2's requirement to quantify how detected inconsistencies affect downstream project controls. The measures show that flagged records can distort project-level cost variance by up to 48.11% and project-level EAC by up to 0.46%, providing empirical evidence for the practical significance of data quality in project cost contexts. This is a novel contribution: the literature identifies data quality as important but does not, to the authors' knowledge, provide a quantified measure of its impact at the project-period granularity used here.

DSR application to data quality: The study demonstrates how the DSR cycle of problem identification, artefact design, demonstration, and evaluation can be applied to a practical problem in project controls. The iterative nature of the implementation, documented through the eight challenges and resolutions in Chapter 4, §4.9, illustrates how DSR accommodates refinement in response to testing outcomes. The eight challenges include architectural refinements (single shared Validator, tier gating, YAML-driven thresholds) that emerged during implementation and are now part of the committed design.

7.3 Practical Implications
Immediate detection: Practitioners can detect malformed submissions at the point of entry rather than discovering them weeks later during periodic reviews. The live API validates incoming records synchronously and returns structured RFC 9457 error responses that identify the specific field, rule, and remediation action that failed (Chapter 4, §4.6).

Continuous monitoring: The dashboard enables tracking of data quality over time and identification of trends that indicate progressive degradation. The multi-mode views allow practitioners to compare batch historical patterns with incremental validation outcomes and live API submission outcomes.

Strict validation standards: The 0.00% false positive rate (Chapter 5, §5.9) suggests that validation can be applied more strictly than originally planned without generating excessive noise. This may allow the rule set to be expanded in future work, increasing detection coverage without compromising usability.

Quantified baseline: The comparison against spreadsheet-based checks (Chapter 6, §6.8) provides a quantitative baseline that practitioners can use to justify investment in automated validation. The finding that spreadsheet-based checks miss 33.33% of logical anomalies is a concrete, measurable deficiency that can be presented to decision-makers.

Demonstrated financial impact: The impact quantification (Chapter 6, §6.7) translates data quality defects into financial terms that practitioners and decision-makers can act on. The finding that a single project's cost variance can be distorted by 48.11% due to flagged records provides a concrete case for prioritising data quality remediation.

7.4 Limitations
Single dataset: The study uses a single publicly available dataset rather than multiple datasets from different organisations. The findings are context-specific, and the framework should be re-tested on additional datasets before being generalised.

Controlled evaluation: The evaluation is limited to system testing and comparative analysis against spreadsheet-based checks. It does not include longitudinal field deployment or real-world user trials. While this limits claims regarding operational usability in broader contexts, it provides a structured, reproducible evaluation under controlled conditions.

API load testing: The live API was tested under controlled malformed submissions but not under concurrent load. The API response time of 1.4 seconds was measured for individual submissions. In operational settings, multiple systems may submit records simultaneously, and the API's behaviour under load has not been tested.

Detection gap: The detection completeness rate of 96.79% (Chapter 5, §5.8) indicates that a small proportion of anomalies still escape detection. The nine undetected anomalies in the test set were concentrated in edge cases involving R8, R9, and R10. The residual gap between 96.79% and 100% is a candidate for future work. Per-tier, this gap is concentrated in project-period rules (95.00%) rather than WBS-level rules (97.78%), suggesting that cross-record and paired-period rules warrant the most attention.

Comparative evaluation test set size: The comparative evaluation against the spreadsheet baseline (Chapter 6, §6.8) uses a 77-record test set with 13 labelled defects, smaller than the 400-record mutation set used in Chapter 5. The smaller size reflects the practical constraint that the spreadsheet baseline is adjudicated manually; the comparison is nonetheless statistically significant for logical anomalies (p < 0.05, Cohen's h = 0.86, large effect). A larger comparative test set would strengthen confidence in the effect size, and this is identified as a future work item.

Persistent storage: The flagged-records log is in-memory (Chapter 4, §4.1 and §4.6). Persistent database storage is identified as a necessary extension for production deployment, as noted in Chapter 4 and reinforced here.

Full Pandera integration: The Pandera schemas serve as the formal declarative specification, while the rule engine enforces equivalent constraints at runtime. Full RAW_CONTRACT.validate() integration is identified as a future enhancement (Chapter 4, §4.4). This does not affect the correctness of detection (the rule engine's constraints are logically equivalent), but it is a design refinement that would make schema enforcement explicit.

7.5 Recommendations for Future Work
Dataset replication: Re-test the framework on additional datasets from different organisations and industries to strengthen external validity and test whether the anomaly patterns observed in the Project Portfolio Dataset are representative of project cost data more broadly.

Load testing: Test the live API under concurrent load to establish whether it maintains acceptable latency under operational conditions and whether any additional infrastructure is required.

Rule expansion: Expand the validation rule set to improve detection completeness, though this would require careful management of the trade-off against false positives. The 0.00% false positive rate (Chapter 5, §5.9) indicates headroom for additional strictness, but the detection gap (96.79%) also indicates that current rules miss edge cases; both dimensions warrant investigation.

User evaluation: Evaluate the dashboard with real users in operational settings to provide evidence on usability, adoption, and the practical impact of the dashboard on decision-making. This would extend the evaluation beyond technical quality to include practical utility in real-world contexts.

Larger comparative test set: Expand the comparative evaluation against the spreadsheet baseline to a larger test set (e.g., 200–400 records) to strengthen the statistical confidence in the effect sizes reported in Chapter 6, §6.9. The current 77-record test set produces a large effect size for logical anomalies (Cohen's h = 0.86) but would benefit from a larger denominator.

Persistent storage and API client integration: Implement persistent database storage for the flagged-records log and a dashboard-side HTTP client for the live API, so that live submissions appear in the dashboard view in real time. Both are identified as future enhancements in Chapter 4.

Impact quantification extension: Extend the impact quantification (Chapter 6, §6.7) to include a wider range of project control indicators — for example, schedule performance index (SPI) alongside CPI, and variance at completion (VAC) alongside EAC — to provide a more complete picture of how data quality defects propagate through project controls.
